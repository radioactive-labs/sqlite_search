# sqlite_search — Hybrid Search (v0.3) Design

- **Date:** 2026-07-24
- **Status:** Approved for planning
- **Builds on:** FTS5 core (v0.1) + vec (v0.2). Fuses an `fts5_scope` and a `vec_scope` on the same model.

## Motivation

Hybrid search combines lexical (FTS5/BM25) and semantic (vector) retrieval, fusing the two ranked lists with Reciprocal Rank Fusion (RRF) and optionally reranking with an app-provided cross-encoder. It is the highest-quality retrieval mode and the endpoint the whole gem was designed toward. This layer adds no new storage — it reuses the model's existing FTS5 and vec indexes.

## Decisions log (settled in brainstorming)

| Decision | Choice |
|---|---|
| Return shape | **Eager `ActiveRecord::Relation`** (like `.semantic`), decorated with a `<name>_score` reader |
| Rerank | **Auto when a reranker is registered**, opt-out via `rerank: false`; best-effort/degradable |
| RRF | `Neighbor::Reranking.rrf(list1, list2, k:)` (already available; no new dep), `k` default 60 |
| Pre-filter | **Native ActiveRecord chaining** — `Post.where(...).search("q")` pre-filters *both* arms (no `within:` argument) |
| Reranker | app-registered `SqliteSearch.reranker do \|query, documents, model:, scope:\| … end`; `documents` = candidate records; returns them reordered |
| Candidate pool | each arm pulls `[limit * 3, 100].min` before fusion |

## Feasibility (verified by probe)

- `Neighbor::Reranking.rrf(list1, list2, k: 60)` returns `[{result:, score:}]` sorted by fused RRF score.
- **Chaining pre-filter works and is exact:** a scope sees the caller's conditions via `all` (`Post.where(tenant_id: 5).published.<scope>` → `all.where_values_hash == {tenant_id: 5, published: true}`); merging that onto the vec arm's join (`Vec.joins("JOIN posts …").merge(caller).nearest_neighbors(…)`) pre-filters the KNN *before* the top-k cut — the exact-nearest row in the wrong tenant is correctly excluded. Because `vec0` KNN is brute-force, `JOIN`+`WHERE` is a true pre-filter, not a post-filter.

## Two parts

### Part A — Chaining pre-filter for `.semantic` (upgrades v0.2)
`vec_scope`'s `.semantic` scope reads the caller's relation and pushes its conditions into the KNN, turning v0.2's documented "filter-after-retrieve" limitation into an exact pre-filter.

```ruby
Post.where(tenant_id: 5).published.semantic("coffee")   # KNN runs only over tenant-5 published rows
```

Mechanism: inside the scope, capture `all.only(:where, :joins)` (the caller's conditions, minus any `order`/`limit`), then:
```ruby
definition.neighbor_model
  .joins("JOIN #{source_table} ON #{source_table}.#{pk} = #{vec_table}.id")
  .merge(caller_conditions)
  .nearest_neighbors(:embedding, vector, distance: :cosine)
  .limit(k)
```
Unchained `Post.semantic("coffee")` → `all` is `Post.all` → no conditions → no pre-filter (unchanged behavior).

### Part B — `hybrid_scope`

```ruby
class Post < ApplicationRecord
  fts5_scope   :by_body,  against: :body
  vec_scope    :semantic, against: :body, dimensions: 768
  hybrid_scope :search, fts5: :by_body, vec: :semantic, k: 60
end

SqliteSearch.reranker do |query, documents, model:, scope:|
  MyReranker.call(query, documents)   # documents = candidate AR records; return them reordered
end
```

- `hybrid_scope(name, fts5:, vec:, k: 60)` validates both named scopes exist on the model (clear error otherwise) and defines `Post.search(query, limit: 20, rerank: true)`.
- Reads the caller's chain and pre-filters both arms (Part A mechanism for the vec arm; normal chaining for the FTS5 arm).

**Pipeline** (`Post.where(...).search("coffee", limit: 20)`):
1. blank/nil query → `.none` (extended so `<name>_score`/chaining stay safe).
2. **FTS5 arm** — the fts5 scope on the (pre-filtered) caller relation, `order_by_rank`, `limit(pool)` → ranked ids.
3. **Vec arm** — the vec scope's KNN, pre-filtered, `k = pool` → ranked ids.
4. **RRF fuse** — `Neighbor::Reranking.rrf(fts_list, vec_list, k: k)` → fused `[{result:{id:}, score:}]`.
5. **Rerank** (if a reranker is registered and not `rerank: false`) — load the top candidates, call `reranker.call(query, records, model:, scope:)` → reordered records; **best-effort**: any exception → log + keep the fused order.
6. **Truncate** to `limit`.
7. Return an eager relation `where(pk => final_ids).order(<rank CASE>)`, decorated with a `<name>_score` reader (the RRF score).

## Reranker contract
- Registered globally via `SqliteSearch.reranker`; a `hybrid_scope` may override with `reranker:`.
- Signature `|query, documents, model:, scope:|`; `documents` is an Array of candidate ActiveRecord records (the fused top candidates); returns the records reordered (a subset is allowed — it truncates naturally at `limit`).
- Synchronous (part of the query, not a background job). Degradable: an exception is rescued, logged via `ActiveSupport::Notifications`/`Rails.logger` if available, and the pre-rerank (RRF) order is used.

## Composability & caveats (documented plainly, no framing)
- `.search` / `.semantic` are **eager**: the embed + both queries + fusion run when the scope is called, not lazily at enumeration. Cost is paid once; the returned relation is then a normal `where(id: …)`.
- **Pre-filter via chaining is exact** for any conditions expressible as SQL on the source table (or tables the caller joins). Ruby-side-only filtering can't be pushed and would post-filter the returned relation instead.
- Trailing `.where` on the returned relation still post-filters (escape hatch); chaining *before* the scope is the correct primary path.

## Error handling
- `hybrid_scope` referencing an undeclared `fts5:`/`vec:` scope → clear `SqliteSearch::Error` at declaration.
- No reranker registered → plain RRF (not an error).
- Reranker raises → degrade to fused order (never fails the query).

## Testing strategy
Stub embedder (from v0.2) + a stub reranker (reverses order, or raises, on demand):
- `.semantic` chaining pre-filter: a tenant-scoped chain excludes the nearest wrong-tenant row.
- `hybrid_scope`: fused order reflects both arms; `<name>_score` exposed; blank → `.none`; composes with `.where`; chaining pre-filters both arms.
- Rerank: reorders when a reranker is registered; `rerank: false` skips it; a raising reranker degrades to fused order (query still succeeds).
- Declaration error for an unknown `fts5:`/`vec:` name.

## Out of scope (v0.3)
- Native `vec0` partition keys (perf lever for very large tenant sets).
- Per-arm score thresholds (v0.3 pulls top-pool from each arm).
- Async reranking (rerank is synchronous within the query).
